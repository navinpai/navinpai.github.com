MCP architecture ↗

An agent is an application that uses model output to choose steps, invoke tools, and use results to continue. The model does not open a network connection itself: application code executes the requested operation. Explain that loop before following arrows.

MCP means Model Context Protocol. The host application uses a client to discover and invoke a server’s tools. A server exposes operations; its handlers may call APIs, databases, or another MCP server. tools/list supplies the available definitions; tools/call invokes a tool. This diagram concentrates on tools; MCP also supports resources and prompts. Transport can be remote HTTP or local standard input/output, called stdio.

Read this picture before using the jargon. The complete investigation is one trace. Each horizontal bar is a span: a named operation with a start, an end, and a status. What is OpenTelemetry? ↗Langfuse ingestion ↗

OpenTelemetry, shortened to OTel, supplies shared telemetry APIs, SDKs, conventions, and export mechanisms. Instrumentation creates the observations; the SDK handles them and sends them onward. Storage and visual inspection belong to the backend. The trace stream goes to two destinations: Langfuse and Aiden for Observability.

OpenLLMetry is a collection of integrations that instruments supported AI libraries using OTel. FastMCP can emit native MCP spans. OTLP, the OpenTelemetry Protocol, carries telemetry to the destinations, directly or through an optional Collector. A Collector can centralize processing and routing.

These are different jobs in a pipeline, not interchangeable products. Verify the actual fields and parent relationships after ingestion. Transition: “Which library supplies each hook? Let’s make that explicit.”

This is conceptual pseudocode for a shared server adapter, not an API to copy from FastMCP. tool_span represents a context manager that activates and ends the span, records thrown exceptions, and restores the previous context on every exit. Production code handles absent or malformed metadata through the propagator. Choose native instrumentation or this hook as the span owner, rather than duplicating both. Keep protocol failure, tool execution failure, and task outcome distinct. A recovered child failure does not automatically mean the parent task failed. Conversely, all operations can execute successfully while the answer lacks adequate evidence.

Spend one minute on each half. First define Server-Sent Events, or SSE, as an HTTP response stream that can stay open while messages arrive. Langfuse's MCP engineering write-up describes long-lived SSE connections skewing ordinary API latency alerts. Measure connection lifetime separately from tools/call, resources/read and other operations. Keep transport health and per-operation latency in separate views. These synthetic bars are schematic, not on a shared time axis; the two short calls can happen during one long connection.

Sentry's engineers describe user timeouts and requests ending without results while their own server view appeared healthy. That is why the right-hand table splits client-observed completions by client/version and transport. All counts here are invented, each out of 100 observed attempts. Completed means a final protocol response arrived before the client's deadline; it does not imply isError=false or a correct agent outcome. Record tool outcome separately. A server-only span cannot prove that the caller received the result.

Capture client name/version where supplied, server build, transport and tool in shared MCP adapters. Keep missing client metadata explicit; client-supplied identity is useful for debugging but is not trusted authentication identity. Timeouts and cancellation belong in client instrumentation, and unexpected disconnects can be observed at the transport edge. An abandonment signal needs a defined lifecycle and observation point; it is not an inference from one missing server span. Compare equivalent tools and workloads before attributing a difference to a client release.

Operational practice: retain connection diagnostics, but alert on operation latency and completion by relevant client cohorts. Check volume changes after releases as a lead for investigation; caches, traffic shifts and adoption also change counts. The practitioner incidents belong to Langfuse and Sentry, not StackGen. The per-client measurement design is our synthesis of their lessons.

These are two independent examples of behavior after an MCP tool error. In the first, the tool tells the agent that its query range is too broad; the next call narrows it and obtains usable evidence. In the second, the server's retry policy repeats a persistent logs permission failure with unchanged credentials and scope. That retry should be stopped and the evidence gap surfaced. Anthropic's engineers recommend examining redundant calls and invalid parameters, and returning actionable errors so agents can recover. Our proposed measurement window begins when the first error reaches the client and ends at usable evidence, a terminal stop or an explicit handoff. Count additional tool attempts in that window, model usage from provider-reported usage, and wall-clock time. Include unresolved windows when reporting recovery rates; do not measure only the successful cases. Unknown tokens remain unknown.

Keep agent self-correction, MCP transport retries, server retries and dependency SDK retries distinguishable by owner and attempt. Two agent attempts times three MCP-client attempts times two dependency attempts can reach twelve downstream attempts if every budget is exhausted.
